## 1. Observability Stack

Choose one metrics path for the cluster so teams are not alerted twice for the same condition:

| Option | Components | Best for |
|---|---|---|
| **AWS-native** | CloudWatch Observability EKS add-on (Container Insights + Fluent Bit), CloudWatch Alarms, SNS | Least operational overhead |
| **Prometheus-based** | Prometheus (or Amazon Managed Service for Prometheus), kube-state-metrics, Alertmanager, Grafana | PromQL alerting, existing Prometheus skills, parity with the local stack |

Both can coexist (CloudWatch for AWS service metrics, Prometheus for in-cluster metrics), as long as each alert has a single owner.

## 2. Centralized Observability Matrix

| Layer | Tooling | Key Metrics / Log Destinations |
|---|---|---|
| Load Balancer | AWS ALB (CloudWatch) | `HTTPCode_Target_2XX/4XX/5XX_Count`, `HTTPCode_ELB_5XX_Count` (502/503/504 generated by the ALB), `TargetResponseTime`, `UnHealthyHostCount`, `RequestCount`. Enable ALB access logs to S3 |
| Kubernetes Cluster | CloudWatch Container Insights and/or Prometheus | Pod CPU and memory, restarts (including OOMKilled), node disk and network, HPA replica count and scaling events |
| Web Server | Nginx container in each pod (TLS ends at the ALB; there is no separate Nginx Ingress controller) | Access logs, slow requests, 502/504 from the PHP-FPM upstream |
| Application | PHP-FPM and Magento 2 | Magento `system.log`, `exception.log`, `debug.log`; **PHP-FPM slow log** (`request_slowlog_timeout` / `slowlog`); PHP-FPM status (active/idle workers, max children reached) |
| Relational Database | Amazon RDS MySQL | Metrics: `CPUUtilization`, `FreeableMemory`, `DatabaseConnections`, `FreeStorageSpace`, `ReadLatency`/`WriteLatency`, `ReplicaLag`. Logs (exported to CloudWatch Logs): error, **slow query log**, general. Performance Insights / Database Insights for query analysis |
| In-Memory Cache | Amazon ElastiCache Redis | `EngineCPUUtilization`, `CPUUtilization`, `DatabaseMemoryUsagePercentage`, `CacheHits`, `CacheMisses`, `Evictions`, `CurrConnections`, `ReplicationLag`. Track the **cache/FPC group and the sessions group separately** |
| Search Engine | Amazon OpenSearch Service | `ClusterStatus.green/yellow/red`, `JVMMemoryPressure`, `SearchLatency`, `IndexingLatency`, `IndexingRate`, `CPUUtilization`, `FreeStorageSpace`, `ClusterIndexWritesBlocked` |
| Message Broker | Amazon MQ (RabbitMQ) | `MessageCount` (per broker and per queue), `QueueCount`, `ConsumerCount`, `ChannelCount`, `ConnectionCount`, `RabbitMQMemUsed` vs `RabbitMQMemLimit`, `RabbitMQDiskFree` vs `RabbitMQDiskFreeLimit`, `SystemCpuUtilization` |
| Shared Media | Amazon EFS | `PercentIOLimit`, `BurstCreditBalance` (if bursting), `ClientConnections` |
| Platform | EKS control plane, VPC, AWS accounts | EKS control-plane logs, VPC Flow Logs, CloudTrail |

> Two common mix-ups: the MySQL *slow query log* is a database log, not a PHP log; and `SlowQueryLog` is a log export you must enable (parameter group plus log export), not a CloudWatch metric.

## 3. Logging Pipeline

1. **Write logs to stdout/stderr**, not to files inside the container. `var/log/*` in a pod is ephemeral and is lost on restart or rescheduling. Configure Magento and PHP-FPM to log to stdout/stderr (or ship the files from a sidecar).
2. **Structured JSON** for Nginx, PHP-FPM and application logs so fields are queryable.
3. **Ship with Fluent Bit** (the CloudWatch Observability add-on deploys it) to CloudWatch Logs, one log group per component.
4. **Set retention** on every log group (for example 30 days hot, longer in S3 if compliance requires) to control cost.
5. **Protect personal data:** Magento logs can contain customer identifiers and request payloads. Mask PII and never log payment data, tokens or secrets.
6. **Enable AWS-side logs:** ALB access logs (S3), RDS log exports, OpenSearch slow logs and error logs, EKS control-plane audit logs, CloudTrail, VPC Flow Logs.
7. Use CloudWatch Logs Insights (or OpenSearch/Grafana Loki) for search; add metric filters for error-rate alarms on `exception.log` patterns.

## 4. Recommended Production Alerts

### 1. RDS MySQL: high CPU or connection exhaustion
- **Condition:** `CPUUtilization > 80%` for 2 consecutive 5-minute periods, **or** `DatabaseConnections` above roughly **80% of `max_connections`**.
- **Why not a fixed 200:** `max_connections` depends on the instance class and parameter group, so a hard-coded number is wrong on most sizes. Calculate the ceiling from your pods: `HPA max replicas x PHP-FPM max children` (plus cron and consumer pods) must fit under `max_connections`.
- **Action:** CloudWatch Alarm -> SNS -> PagerDuty. First checks: Performance Insights top SQL, slow query log, recent deploys or reindex jobs.

```bash
aws cloudwatch put-metric-alarm \
  --alarm-name magento-rds-cpu-high \
  --namespace AWS/RDS --metric-name CPUUtilization \
  --dimensions Name=DBInstanceIdentifier,Value=<db-instance-id> \
  --statistic Average --period 300 --evaluation-periods 2 \
  --threshold 80 --comparison-operator GreaterThanThreshold \
  --treat-missing-data notBreaching \
  --alarm-actions <sns-topic-arn>
```

### 2. ElastiCache Redis: memory saturation
- **Condition:** `DatabaseMemoryUsagePercentage > 85%` on the **sessions** group; `Evictions > 0` sustained on the sessions group; `EngineCPUUtilization > 80%`.
- **Action:** notify on-call and open a capacity ticket. **Do not auto-resize.** Changing node type is a planned operation that causes a failover, and in the cluster-mode-disabled design used here you cannot add shards to spread memory. Adding replicas helps reads, not memory.
- **Cache/FPC group:** a full cache group at `allkeys-lru` is normal behaviour, so a plain 85% memory alarm is noisy. Alert on a falling hit ratio (`CacheHits / (CacheHits + CacheMisses)`) and unusually high eviction rate instead.
- **Sessions group** (`noeviction`): reaching 100% means writes fail and customers cannot log in or keep a cart, so treat it as high severity.

### 3. Application Load Balancer: 5XX
- **Condition:** target 5XX **rate** above about 2% of `RequestCount` for 3 of 5 minutes, with a minimum request-volume guard (CloudWatch metric math: `HTTPCode_Target_5XX_Count / RequestCount * 100`). An absolute "more than 10 per minute" does not scale with traffic. Create a second alarm on `HTTPCode_ELB_5XX_Count` (502/503/504 from the ALB itself) and on `UnHealthyHostCount > 0`.
- **Runbook hints (not the action itself):** target 5XX usually points to PHP errors, PHP-FPM worker exhaustion (`max children reached`) or database/Redis failures; ELB 5XX points to no healthy targets, timeouts or a bad rollout. Check pod readiness, `kubectl rollout status`, PHP-FPM status and RDS connections.

### 4. Pod CrashLoopBackOff / restarts
- **Condition:** any Magento container restarting more than 3 times in 10 minutes.
- **How it's detected:** restart counters come from **kube-state-metrics** (or Container Insights), not from Kubernetes events. Prometheus does not capture events; use an event exporter if you want them.
- **Check OOMKilled:** with a 4.5 GB memory limit, restarts are often out-of-memory kills.

```yaml
groups:
  - name: magento-k8s
    rules:
      - alert: MagentoPodRestarting
        expr: increase(kube_pod_container_status_restarts_total{namespace="magento"}[10m]) > 3
        labels:
          severity: page
        annotations:
          summary: "{{ $labels.pod }} restarted more than 3 times in 10 minutes"
      - alert: MagentoPodCrashLoop
        expr: kube_pod_container_status_waiting_reason{namespace="magento",reason="CrashLoopBackOff"} == 1
        for: 5m
        labels:
          severity: page
```

## 5. Additional Alerts

| Alert | Condition (starting point) | Why |
|---|---|---|
| RDS free storage / memory | `FreeStorageSpace` low (for example < 20%), sustained low `FreeableMemory` | Autoscaling storage has limits; memory pressure slows queries |
| RDS replica lag | `ReplicaLag` above your tolerance | Stale reads and DR replica staleness |
| OpenSearch red/yellow | `ClusterStatus.red >= 1` (page), `ClusterStatus.yellow` for 15+ min | Search outage or missing replicas |
| OpenSearch JVM / storage | `JVMMemoryPressure > 80%`, low `FreeStorageSpace`, `ClusterIndexWritesBlocked >= 1` | Prevents blocked indexing and node instability |
| RabbitMQ memory / disk | `RabbitMQMemUsed` near `RabbitMQMemLimit`, `RabbitMQDiskFree` near the limit | RabbitMQ blocks publishers when its alarms trigger |
| Queue backlog | `MessageCount` growing for N minutes on a queue, or `ConsumerCount = 0` | Async operations (orders, inventory, exports) stall |
| Magento cron health | CronJob failing, or last successful schedule older than a few minutes | Indexing, emails and queues depend on cron |
| HPA at max | Replicas at `maxReplicas` for 15+ minutes | Capacity ceiling reached |
| EFS performance | `PercentIOLimit` high, low `BurstCreditBalance` | Slow media reads and writes |
| Node health | Node `NotReady`, high disk or memory pressure | Pod rescheduling and capacity loss |
| Backups | AWS Backup job failed or latest restorable time older than the RPO | Ties to the Backup & DR strategy |
| Certificates | ACM certificate `DaysToExpiry` low | ACM renews automatically only when DNS validation records remain in place |

## 6. Alert Routing & Severity

| Severity | Examples | Route |
|---|---|---|
| **Page** (act now) | ALB 5XX rate, no healthy targets, OpenSearch red, sessions Redis full, RDS CPU or connections exhausted, CrashLoopBackOff | CloudWatch -> SNS -> PagerDuty / Alertmanager receiver |
| **Ticket** (business hours) | Capacity trends, yellow cluster status, hit-ratio drop, HPA at max | Email / Slack / ticket queue |
| **Info** | Deployments, scaling events | Dashboards and channel notifications |

Every paging alert should link to a runbook, use `treat-missing-data` deliberately, and require several evaluation periods to avoid flapping.

---

## 7. Dashboards & SLOs

- Grafana (or CloudWatch dashboards): one overview (traffic, error rate, p95 latency, pod count, DB/Redis/OpenSearch/RabbitMQ health) plus one per component.
- Define a few SLOs and alert on burn rate rather than on every symptom: storefront availability, p95 page latency, and checkout success rate.
- Review alert noise after each incident and tune thresholds from real baselines.
